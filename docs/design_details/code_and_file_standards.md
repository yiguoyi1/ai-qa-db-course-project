# 代码与文件管理规范

## 1. 文档目的

本规范用于统一本项目在代码组织、文件命名、脚本编写、SQL 管理、文档维护和敏感信息处理方面的约定，目标是：

- 保证仓库结构清晰，便于课程设计展示和后续维护
- 保证 SQL、脚本和文档之间能够互相对应
- 降低多人协作或多次迭代时的混乱风险
- 避免配置文件、密码和临时文件被误提交

## 2. 仓库目录规范

当前仓库建议按以下职责分层管理：

- `sql/`
  保存数据库对象脚本，按对象类型拆分，不混写到同一个超大文件中。
- `scripts/`
  保存本地执行脚本，如启动数据库、导入 schema、校验 schema 等自动化脚本。
- `docker/`
  保存容器启动相关文件，包括初始化脚本、镜像启动附加配置等。
- `docs/design_details/`
  保存产品设计、数据设计、流程说明、约束规范等设计类文档。
- `docs/setup/`
  保存环境搭建、依赖安装、运行步骤等部署类文档。
- `docs/diagrams/`
  保存 ER 图、流程图、架构图等图片或图形资料。
- `docs/report/`
  预留用于课程报告、答辩材料或阶段总结。

管理原则：

- 配置文件、脚本、SQL、文档分目录管理，不混放
- 同一目录下的文件应服务于同一类职责
- 临时文件、导出文件、测试废稿不进入正式目录

## 3. 文件命名规范

### 3.1 通用命名规则

- 文件名统一使用英文和数字，推荐 `kebab-case` 或 `snake_case`
- 不使用中文文件名
- 不使用空格
- 文件名应体现职责，而不是使用 `test1`、`new`、`final` 之类无语义名称

### 3.2 本项目建议

- SQL 文件使用 `snake_case`
  例如：`create_tables.sql`、`procedures.sql`、`triggers.sql`
- PowerShell 脚本使用 `kebab-case`
  例如：`start-oracle26ai.ps1`、`load-oracle-schema.ps1`
- 设计文档使用 `snake_case`
  例如：`data_design.md`、`constraints_and_rules.md`

## 4. SQL 文件管理规范

### 4.1 拆分原则

数据库脚本按职责拆分，当前建议保持如下结构：

- `create_tables.sql`
  管理表、主键、外键、唯一约束、检查约束和索引
- `procedures.sql`
  管理存储过程、函数、包和包体
- `triggers.sql`
  管理触发器
- 后续如需要新增视图、初始化数据、权限脚本，可继续拆分为：
  - `views.sql`
  - `seed_data.sql`
  - `grants.sql`

### 4.2 编写规范

- 所有数据库对象使用英文命名
- 不使用带双引号的对象名
- 表、列、约束、索引、包、触发器命名要体现业务语义
- 同一类对象保持统一前缀风格
  例如：
  - 主键：`pk_`
  - 外键：`fk_`
  - 唯一约束：`uq_`
  - 检查约束：`ck_`
  - 索引：`idx_`
  - 触发器：`trg_`

### 4.3 内容顺序规范

`create_tables.sql` 中建议按以下顺序组织：

1. 基础主表
2. 关联表
3. 行为表
4. 推荐和画像表
5. AI 扩展表
6. 日志和管理表
7. 索引

`procedures.sql` 中建议按以下顺序组织：

1. 包声明
2. 包体
3. 公共函数
4. 公共过程

`triggers.sql` 中建议按以下顺序组织：

1. 问题统计触发器
2. 回答统计触发器
3. 登录同步触发器
4. 其他审计或业务触发器

### 4.4 SQL 变更原则

- 一次变更尽量只解决一类问题
- 修改约束时同步更新文档
- 修改统计逻辑时同步检查触发器和过程
- 修改枚举值时同步检查：
  - 建表脚本
  - 过程逻辑
  - 触发器逻辑
  - 校验脚本
  - 设计文档

## 5. 脚本代码规范

### 5.1 PowerShell 脚本规范

- 脚本职责单一
  例如启动数据库、导入 schema、验证 schema 分开管理
- 关键步骤需要输出清晰提示，便于运行时定位问题
- 对失败步骤应尽量给出明确错误信息
- 参数名、变量名使用英文，语义清晰
- 避免把账号密码直接硬编码进脚本

### 5.2 Docker 相关文件规范

- `compose.yaml` 只负责容器编排
- 启动时执行的数据库初始化逻辑放到 `docker/oracle/startup/`
- 与镜像版本、端口、密码相关的可变内容尽量走 `.env`
- 不在文档和脚本里写死真实密码

## 6. 文档管理规范

### 6.1 文档分类

- 产品设计写入 `docs/design_details/`
- 环境搭建写入 `docs/setup/`
- 图示资料写入 `docs/diagrams/`
- 答辩或报告材料放入 `docs/report/`

### 6.2 文档内容要求

- 文档应使用正式、可交付的语气
- 文档内容要与实际代码和 SQL 保持一致
- 文档不写“暂定但未实现”为已完成能力
- 如果是预留能力，应明确标注“预留”“待扩展”“当前未落地”

### 6.3 文档更新原则

- 改数据库结构时同步改设计文档
- 改业务流程时同步改数据流文档
- 改推荐逻辑时同步改产品设计与约束说明
- 改部署方式时同步改 README 和 setup 文档

## 7. 敏感信息与配置文件规范

### 7.1 不允许提交的内容

以下内容不得提交到仓库：

- 真实数据库密码
- 真实 Oracle Registry 凭据
- 真实 `.env`
- 本地绝对路径配置
- 临时导出的日志、SQL 转储、缓存文件

### 7.2 允许提交的内容

- `.env.example`
- 脱敏后的示例配置
- 不含隐私数据的演示截图
- 脱敏后的测试数据样例

### 7.3 配置管理原则

- 所有敏感配置统一通过 `.env` 注入
- `.env.example` 只保留字段名和示例值
- `.gitignore` 必须忽略 `.env`、缓存和临时文件

## 8. Git 与版本管理规范

### 8.1 提交原则

- 一次提交只做一类事情
  例如“补约束”“补文档”“修触发器”应尽量分开
- 提交前确保当前修改能自圆其说，不留下半成品
- 不把无关格式化、测试垃圾文件混入一次提交

### 8.2 提交信息建议

推荐使用简洁中文或中英混合说明，例如：

- `完善产品设计与数据流文档`
- `补充 answer_feedback 唯一约束`
- `统一 login_log.result 为三态`
- `新增 Oracle 26ai schema 校验脚本`

### 8.3 分支与阶段管理建议

- 主分支保留可演示、可交付版本
- 大改动建议单独分支开发
- 阶段性成果可按“环境搭建完成、DDL 完成、过程触发器完成、文档完善完成”进行整理

## 9. 数据库对象与文档一致性规范

为避免“文档是一套、代码是一套”，本项目要求：

- 约束文档必须能在 DDL 中找到对应实现
- 业务流程文档必须能在表结构、过程或触发器中找到落点
- 产品文档中的已实现能力，必须可通过脚本或 SQL 证明
- 当前仅预留未实现的能力，必须在文档中明确说明

建议每次做以下一致性检查：

1. 表结构字段是否与数据表说明一致
2. 状态枚举是否与约束说明一致
3. 触发器是否与统计同步规则一致
4. 存储过程是否与推荐流程说明一致
5. README 是否与真实启动方式一致

## 10. 提交前检查清单

每次准备提交或交付前，建议按以下顺序检查：

1. `sql/` 中对象是否可以编译
2. 约束、触发器、过程是否与文档一致
3. `.env` 是否未提交
4. 文档中的路径、密码、账号是否已脱敏
5. README 中的启动步骤是否可执行
6. 验证脚本是否仍可运行

## 11. 当前项目的落地建议

结合本仓库当前状态，建议后续持续遵守以下规则：

- 所有数据库逻辑优先落在 `sql/` 中，不要把核心逻辑写死在文档里
- 所有运行入口优先集中到 `scripts/`
- 所有设计说明优先写入 `docs/design_details/`
- 所有部署说明优先写入 `docs/setup/`
- 每完成一类功能，就同步补一类文档
- 每次修改推荐、约束或登录逻辑，都重新跑一次 schema 校验

## 12. 总结

代码与文件管理规范的核心不是“格式好看”，而是让项目在以下三方面保持稳定：

- 能快速找到文件
- 能说清楚每个文件负责什么
- 能保证文档、SQL、脚本和实际行为一致

对课程设计项目来说，这份规范还能直接帮助你提升交付质量和答辩说服力。
