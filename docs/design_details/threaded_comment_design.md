# 楼中楼评论设计

## 1. 设计目标

本设计用于补齐问答社区中“回答下的评论与回复”能力，使平台从“问题 - 回答 - 反馈”进一步扩展为“问题 - 回答 - 评论 - 回复”的完整社区交流结构。

本设计强调三点：

- 与当前问答社区定位保持一致
- 与现有 `ANSWERS`、`USERS`、`ANSWER_FEEDBACK` 结构解耦但协同
- 为后续建表、接口实现、CLI 测试和答辩说明提供直接依据

## 2. 为什么需要楼中楼

当前系统已经支持：

- 问题下的多回答
- 人工回答与 AI 回答并存
- 对回答的点赞、点踩、评分和简短备注

但当前还不支持真正的社区讨论，因为：

- `ANSWER_FEEDBACK.COMMENT_TEXT` 只是“反馈备注”
- 它不具备评论树结构
- 它无法表达“回复某条评论”
- 它不适合承载持续交流

因此，若要让“用户之间也能交流”成立，必须新增独立的评论/回复结构。

## 3. 产品交互模型

### 3.1 交互对象

楼中楼评论的挂载对象应是“回答”，而不是“问题”。

推荐原因：

- 问题是讨论主题
- 回答是具体观点和解法
- 评论和回复通常是围绕某条回答展开的补充、追问、反驳或认可

因此，推荐模型为：

- 问题
  - 回答
    - 一级评论
      - 回复评论
        - 继续回复

### 3.2 典型场景

场景 1：补充说明  
用户看到一条回答后，在其下发表评论，补充自己的理解。

场景 2：追问回答者  
用户对某条回答不理解，直接在回答下提问。

场景 3：用户之间讨论  
用户 A 发表一级评论，用户 B 回复用户 A，用户 C 再回复用户 B，形成楼中楼。

场景 4：AI 回答下的人类讨论  
即便回答来源是 `AI`，其下仍可由社区用户继续讨论。

## 4. 推荐的交互规则

### 4.1 评论层级

推荐采用：

- 数据层支持树形结构
- 展示层默认展示“两层可见 + 深层折叠”

具体解释：

- 数据库允许通过 `parent_comment_id` 形成任意树结构
- 但页面或 CLI 默认只直接展开：
  - 一级评论
  - 一级评论下的回复
- 更深层的回复可继续存在，但默认折叠到所属评论线程下

这样做的好处是：

- 数据结构灵活
- 展示复杂度可控
- 不会因为 UI 先天限制把数据结构锁死

### 4.2 评论入口

建议提供两种创建动作：

1. 发表评论  
   直接挂在某条回答下，属于一级评论。

2. 回复评论  
   挂在某条已有评论下，形成楼中楼。

### 4.3 排序规则

建议按“线程”和“回复”分开排序：

- 一级评论：支持 `new` / `hot`
- 回复列表：默认按时间正序

推荐默认行为：

- 一级评论默认按最新时间倒序
- 同一评论线程中的回复按时间升序

### 4.4 删除规则

评论删除推荐采用“软删除”而不是直接硬删除。

理由：

- 评论节点可能已经有子回复
- 直接硬删会破坏整棵讨论树
- 软删后可以保留楼层关系

软删除后的展示建议：

- 顶层评论显示为“原评论已删除”
- 回复评论显示为“原回复已删除”
- 保留作者、时间、回复层级和子评论

## 5. 数据模型设计

## 5.1 推荐新增表

建议新增：

- `ANSWER_COMMENTS`

推荐字段如下：

| 字段名 | 类型建议 | 含义 |
| --- | --- | --- |
| `COMMENT_ID` | `NUMBER` | 评论主键 |
| `ANSWER_ID` | `NUMBER NOT NULL` | 所属回答 |
| `USER_ID` | `NUMBER NOT NULL` | 评论作者 |
| `PARENT_COMMENT_ID` | `NUMBER NULL` | 直接父评论，一级评论为 `NULL` |
| `ROOT_COMMENT_ID` | `NUMBER NULL` | 所属评论线程根节点，顶层评论创建后会回填为自身 `COMMENT_ID` |
| `REPLY_TO_USER_ID` | `NUMBER NULL` | 当前评论直接回复的用户，由服务层根据父评论自动推导 |
| `CONTENT` | `CLOB` | 评论内容 |
| `COMMENT_LEVEL` | `NUMBER NOT NULL` | 评论层级 |
| `STATUS` | `VARCHAR2(20 CHAR)` | 评论状态 |
| `REPLY_COUNT` | `NUMBER DEFAULT 0` | 当前评论的直接回复数 |
| `CREATE_TIME` | `DATE DEFAULT SYSDATE` | 创建时间 |
| `UPDATE_TIME` | `DATE DEFAULT SYSDATE` | 最近更新时间 |
| `DELETE_TIME` | `DATE NULL` | 删除时间 |

### 5.2 字段设计说明

`PARENT_COMMENT_ID`

- 用于表达“我回复的是哪条评论”
- 一级评论为 `NULL`

`ROOT_COMMENT_ID`

- 用于快速定位当前评论所属的整条线程
- 一级评论创建时允许先为 `NULL`，插入成功后再回填为 `COMMENT_ID`
- 回复评论的 `ROOT_COMMENT_ID = 所属线程的一级评论 COMMENT_ID`

`REPLY_TO_USER_ID`

- 用于更清楚表达“回复给谁”
- 即使前端展示为“回复 @某用户”，也不需要额外解析父评论

`COMMENT_LEVEL`

- 用于减少查询和展示判断成本
- 一级评论为 `1`
- 回复为 `父评论级别 + 1`

### 5.3 推荐 DDL 草案

```sql
CREATE TABLE answer_comments (
    comment_id         NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY,
    answer_id          NUMBER             NOT NULL,
    user_id            NUMBER             NOT NULL,
    parent_comment_id  NUMBER,
    root_comment_id    NUMBER,
    reply_to_user_id   NUMBER,
    content            CLOB               NOT NULL,
    comment_level      NUMBER             DEFAULT 1        NOT NULL,
    status             VARCHAR2(20 CHAR)  DEFAULT 'ACTIVE' NOT NULL,
    reply_count        NUMBER             DEFAULT 0        NOT NULL,
    create_time        DATE               DEFAULT SYSDATE  NOT NULL,
    update_time        DATE               DEFAULT SYSDATE  NOT NULL,
    delete_time        DATE,
    CONSTRAINT pk_answer_comments PRIMARY KEY (comment_id),
    CONSTRAINT fk_answer_comments_answer
        FOREIGN KEY (answer_id) REFERENCES answers (answer_id),
    CONSTRAINT fk_answer_comments_user
        FOREIGN KEY (user_id) REFERENCES users (user_id),
    CONSTRAINT fk_answer_comments_parent
        FOREIGN KEY (parent_comment_id) REFERENCES answer_comments (comment_id),
    CONSTRAINT fk_answer_comments_root
        FOREIGN KEY (root_comment_id) REFERENCES answer_comments (comment_id),
    CONSTRAINT fk_answer_comments_reply_to_user
        FOREIGN KEY (reply_to_user_id) REFERENCES users (user_id),
    CONSTRAINT ck_answer_comments_status CHECK (
        status IN ('ACTIVE', 'HIDDEN', 'DELETED')
    ),
    CONSTRAINT ck_answer_comments_level CHECK (comment_level >= 1),
    CONSTRAINT ck_answer_comments_reply_count CHECK (reply_count >= 0),
    CONSTRAINT ck_answer_comments_delete_time CHECK (
        delete_time IS NULL OR delete_time >= create_time
    )
);
```

### 5.4 推荐索引

```sql
CREATE INDEX idx_answer_comments_answer_id ON answer_comments (answer_id);
CREATE INDEX idx_answer_comments_parent_id ON answer_comments (parent_comment_id);
CREATE INDEX idx_answer_comments_root_id ON answer_comments (root_comment_id);
CREATE INDEX idx_answer_comments_user_id ON answer_comments (user_id);
CREATE INDEX idx_answer_comments_create_time ON answer_comments (create_time);
```

## 6. 核心约束与业务规则

### 6.1 基础规则

- 评论必须属于一条已存在的回答
- 评论必须由一个已存在用户创建
- 一级评论：`parent_comment_id IS NULL`
- 一级评论：`root_comment_id = comment_id`
- 回复评论：`parent_comment_id IS NOT NULL`
- 回复评论：`root_comment_id = 父链路上的根评论`

### 6.2 一致性规则

必须保证：

- `parent_comment_id` 和 `root_comment_id` 指向的评论都属于同一个 `answer_id`
- 不能回复其他回答下的评论
- 允许用户在自己的评论线程下继续补充说明或追问

建议在 service 层做校验：

- 父评论是否存在
- 父评论是否为 `ACTIVE`
- 父评论的 `answer_id` 是否与当前回答一致

### 6.3 状态规则

推荐状态：

- `ACTIVE`：正常显示
- `HIDDEN`：预留给后续治理或审核场景
- `DELETED`：用户删除或系统软删

推荐行为：

- `ACTIVE` 可回复
- `HIDDEN` 默认不可回复
- `DELETED` 不可继续回复

### 6.4 内容规则

- 内容不能为空
- 内容长度建议限制在 1000 字以内
- 当前实现不开放评论编辑
- 删除后写入 `DELETE_TIME`

### 6.5 问题状态联动规则

建议评论权限与问题状态联动：

- `OPEN`：允许评论和回复
- `RESOLVED`：仍允许评论和补充讨论
- `CLOSED`：不允许新增评论
- `ARCHIVED`：只读，不允许新增评论

这样既符合社区语义，也便于后续治理。

## 7. 接口设计

### 7.1 推荐第一版接口

建议先做这 3 个：

1. `POST /api/answers/{answer_id}/comments`
2. `GET /api/answers/{answer_id}/comments`
3. `DELETE /api/comments/{comment_id}`

### 7.2 创建评论

`POST /api/answers/{answer_id}/comments`

请求体建议：

```json
{
  "user_id": 22,
  "content": "我觉得这个回答还可以再补充一下事务处理。",
  "parent_comment_id": null
}
```

规则：

- `parent_comment_id = null` 时表示一级评论
- 非空时表示回复某条评论
- `reply_to_user_id` 由后端根据父评论自动计算，不需要调用方传入

### 7.3 查询评论树

`GET /api/answers/{answer_id}/comments`

当前实现：

- 一级评论列表
- 每条一级评论下附带其直接回复列表
- 当前不提供排序、分页参数
- 如需更深层展开，可在后续版本增加 `expand_replies=true` 或分页能力

### 7.4 删除评论

`DELETE /api/comments/{comment_id}`

建议参数：

- `user_id`

规则：

- 当前仅评论作者本人可删除
- 删除采用软删除
- 删除后不级联删除子回复
- 查询评论树时，已删除顶层评论显示为“原评论已删除”
- 查询评论树时，已删除回复显示为“原回复已删除”

## 8. 返回结构建议

建议定义如下响应模型：

```json
{
  "comment_id": 101,
  "answer_id": 82,
  "user_id": 22,
  "author_username": "demo_reader",
  "author_nickname": "Demo Reader",
  "parent_comment_id": null,
  "root_comment_id": 101,
  "reply_to_user_id": null,
  "reply_to_username": null,
  "reply_to_nickname": null,
  "content": "这个回答可以再解释一下。",
  "comment_level": 1,
  "status": "ACTIVE",
  "reply_count": 2,
  "create_time": "2026-04-05T10:00:00",
  "update_time": "2026-04-05T10:00:00",
  "children": []
}
```

这样前端或 CLI 可直接构造树形展示。

## 9. Service 层建议

建议新增：

- `comment_service.py`
- `comment_repository.py`
- `comments.py` 路由

推荐职责如下：

`comment_service`

- 校验回答是否存在
- 校验问题状态是否允许评论
- 校验父评论是否存在
- 计算 `root_comment_id`
- 计算 `comment_level`
- 执行创建、查询、删除逻辑

`comment_repository`

- 插入评论
- 查询评论树
- 软删除评论
- 查询父评论与根评论信息
- 顶层评论创建后回填 `root_comment_id`
- 回复评论创建后维护父评论 `reply_count`

## 10. 与现有模块的关系

### 10.1 与 `ANSWER_FEEDBACK` 的关系

`ANSWER_FEEDBACK` 继续负责：

- 点赞
- 点踩
- 评分
- 简短质量备注

`ANSWER_COMMENTS` 负责：

- 讨论
- 回复
- 楼中楼

两者不要混用。

### 10.2 与 `ANSWERS` 的关系

评论是挂在回答下的次级内容。

因此：

- 先有回答
- 再有评论

没有回答就不应该有评论。

### 10.3 与推荐的关系

第一阶段不建议把评论行为直接纳入推荐权重。

原因：

- 评论更多体现交流活跃度
- 其兴趣信号通常不如浏览、收藏、反馈直接

第二阶段可考虑：

- 评论回答时，将回答所属问题标签作为弱兴趣信号加入画像

## 11. CLI 与展示建议

如果未来在 CLI 中补楼中楼，建议支持：

- 查看回答评论
- 发表评论
- 回复评论
- 删除评论

展示建议：

```text
[回答 82]
  ├─ 评论 101 by demo_reader
  │  ├─ 回复 102 by demo_owner
  │  └─ 回复 103 by demo_reader
  └─ 评论 104 by api_test_user
```

## 12. 测试建议

楼中楼实现后，至少应覆盖这些测试：

1. 一级评论创建成功
2. 回复评论创建成功
3. 回复的 `root_comment_id` 正确
4. 不允许跨回答回复
5. 删除父评论后子评论仍保留
6. `CLOSED` / `ARCHIVED` 问题不允许新增评论
7. 非作者不能删除评论
8. 已删除评论与已删除回复会按占位文案展示

## 13. 推荐开发顺序

最合理的顺序是：

1. 建表 `ANSWER_COMMENTS`
2. 实现创建评论接口
3. 实现查询评论树接口
4. 实现软删除与占位展示
5. CLI 补充评论入口
6. 再考虑评论点赞、通知、管理员审核

## 14. 结论

如果你要做真正的“问答社区楼中楼”，最稳的方案不是扩展 `ANSWER_FEEDBACK`，而是：

- 单独新增 `ANSWER_COMMENTS`
- 用 `parent_comment_id + root_comment_id + comment_level` 构造评论树
- 数据层支持完整线程
- 展示层默认两层展开，深层折叠

这样既保留了社区讨论能力，也不会把现有回答反馈模型搅乱。
## 15. 当前实现补充说明

当前代码实现已经采用以下口径，并以此为准：

- 评论支持创建、查询和删除
- 评论不支持编辑
- 删除采用软删除
- 删除评论时不会级联删除其子回复
- 顶层评论创建后会回填 `root_comment_id`
- `reply_to_user_id` 由服务层自动根据父评论推导
- 当前 `REPLY_COUNT` 维护的是直接回复数量
- 查询评论树时，已删除顶层评论显示为“原评论已删除”
- 查询评论树时，已删除回复显示为“原回复已删除”
