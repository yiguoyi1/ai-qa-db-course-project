# 头像与图片能力设计

## 1. 设计目标

当前项目已经具备问答社区、AI 首答、人工回答、评论与推荐等基础能力，但还缺少社区产品中常见的两类媒体能力：

- 用户头像
- 内容图片

这份设计文档的目标是：

1. 为“头像上传与展示”提供一套可直接实现的方案
2. 为“问题 / 回答配图”提供一套与当前项目结构兼容的方案
3. 控制第一阶段复杂度，避免一上来把项目做成完整媒体系统

因此，这里采用的原则是：

- 第一阶段先解决“能用”
- 第二阶段再考虑“更完整”
- 数据库存元数据，文件不直接存进 Oracle BLOB

## 2. 当前缺口

基于当前实现，项目还没有以下能力：

- `USERS` 中没有头像字段
- `QUESTIONS` / `ANSWERS` / `ANSWER_COMMENTS` 中没有图片元数据结构
- 后端没有文件上传接口
- 前端没有头像或图片展示区域
- 数据库没有统一媒体资源表

因此，这项能力需要从“数据结构 + API + 存储路径 + 页面展示”四层一起补。

## 3. 迭代策略

建议按 4 个阶段逐步落地：

### 3.1 第一阶段：头像 MVP

目标：

- 用户可以上传头像
- 登录后和内容列表中可以显示头像

范围：

- 支持单张头像
- 支持替换头像
- 不支持头像裁剪、缩放、圆角模板、历史版本

### 3.2 第二阶段：问题配图

目标：

- 用户发布问题时可以上传图片
- 问题详情页可以查看问题配图

范围：

- 每个问题最多若干张图
- 不做高级图册管理

### 3.3 第三阶段：回答配图

目标：

- 用户回答时可以附图
- 回答区可展示配图

范围：

- 仅支持图片
- 不支持视频、文档、音频

### 3.4 第四阶段：增强项

可选增强：

- 评论发图
- 图片懒加载
- 缩略图
- 图片审核
- 管理员隐藏媒体
- 对象存储迁移

第一版不建议直接做第四阶段。

## 4. 推荐总体方案

### 4.1 文件存储策略

建议采用：

- 文件存在本地目录
- 数据库存媒体元数据

原因：

- 当前项目是课程设计 / 问答社区 MVP
- 本地开发和演示优先
- 用本地目录存储最容易落地
- 后续如果迁移到 MinIO / OSS / COS，也只需要替换存储实现层

第一版不建议：

- 直接把图片二进制存进 Oracle BLOB
- 一开始就接第三方对象存储

### 4.2 推荐目录结构

建议新增：

- `uploads/avatars/`
- `uploads/questions/`
- `uploads/answers/`

文件命名建议：

- 不保留原始文件名作为最终文件名
- 使用 `时间戳 + 随机串` 或 `UUID`

例如：

- `uploads/avatars/20260422_ab12cd34.png`
- `uploads/questions/20260422_ef56gh78.jpg`
- `uploads/answers/20260422_ij90kl12.webp`

### 4.3 推荐访问方式

建议由 FastAPI 提供静态访问入口，例如：

- `/uploads/avatars/...`
- `/uploads/questions/...`
- `/uploads/answers/...`

这样网页前端和 CLI 返回的媒体 URL 可以统一。

## 5. 数据库设计

## 5.1 新增统一媒体表

建议新增表：`MEDIA_ASSETS`

推荐字段如下：

| 字段 | 类型建议 | 含义 |
| --- | --- | --- |
| `media_id` | `NUMBER IDENTITY` | 主键 |
| `uploader_user_id` | `NUMBER NOT NULL` | 上传者 |
| `owner_type` | `VARCHAR2(30 CHAR)` | 媒体归属类型 |
| `owner_id` | `NUMBER NOT NULL` | 归属对象 ID |
| `file_name` | `VARCHAR2(120 CHAR)` | 服务器保存名 |
| `original_file_name` | `VARCHAR2(255 CHAR)` | 原始文件名 |
| `mime_type` | `VARCHAR2(100 CHAR)` | MIME 类型 |
| `file_ext` | `VARCHAR2(20 CHAR)` | 文件扩展名 |
| `file_size` | `NUMBER` | 文件大小，单位字节 |
| `storage_path` | `VARCHAR2(255 CHAR)` | 本地存储路径 |
| `public_url` | `VARCHAR2(255 CHAR)` | 对外访问 URL |
| `sort_order` | `NUMBER DEFAULT 1` | 展示顺序 |
| `status` | `VARCHAR2(20 CHAR)` | 媒体状态 |
| `create_time` | `DATE DEFAULT SYSDATE` | 创建时间 |
| `update_time` | `DATE DEFAULT SYSDATE` | 更新时间 |
| `delete_time` | `DATE` | 软删除时间 |

### 5.2 `owner_type` 推荐枚举

建议允许：

- `USER_AVATAR`
- `QUESTION`
- `ANSWER`

第一阶段先只支持这三类。

### 5.3 推荐约束

建议约束：

- `fk_media_assets_uploader`
  - `uploader_user_id -> users.user_id`
- `ck_media_assets_owner_type`
  - `owner_type IN ('USER_AVATAR', 'QUESTION', 'ANSWER')`
- `ck_media_assets_status`
  - `status IN ('ACTIVE', 'DELETED')`
- `ck_media_assets_file_size`
  - `file_size >= 0`
- `ck_media_assets_sort_order`
  - `sort_order >= 1`

### 5.4 推荐索引

建议索引：

- `idx_media_assets_owner`
  - `(owner_type, owner_id, status, sort_order)`
- `idx_media_assets_uploader`
  - `(uploader_user_id)`
- `idx_media_assets_create_time`
  - `(create_time)`

## 5.5 用户头像字段设计

建议在 `USERS` 中新增：

- `avatar_media_id NUMBER`

并建立外键：

- `fk_users_avatar_media -> media_assets.media_id`

这样做比直接加 `avatar_url` 更适合当前项目，因为：

- 头像也能纳入统一媒体管理
- 后续支持头像替换、状态管理、清理策略会更容易
- 跟问题 / 回答图片共用同一套媒体机制

## 6. DDL 草案

```sql
CREATE TABLE media_assets (
    media_id             NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY,
    uploader_user_id     NUMBER             NOT NULL,
    owner_type           VARCHAR2(30 CHAR)  NOT NULL,
    owner_id             NUMBER             NOT NULL,
    file_name            VARCHAR2(120 CHAR) NOT NULL,
    original_file_name   VARCHAR2(255 CHAR),
    mime_type            VARCHAR2(100 CHAR) NOT NULL,
    file_ext             VARCHAR2(20 CHAR),
    file_size            NUMBER             DEFAULT 0 NOT NULL,
    storage_path         VARCHAR2(255 CHAR) NOT NULL,
    public_url           VARCHAR2(255 CHAR) NOT NULL,
    sort_order           NUMBER             DEFAULT 1 NOT NULL,
    status               VARCHAR2(20 CHAR)  DEFAULT 'ACTIVE' NOT NULL,
    create_time          DATE               DEFAULT SYSDATE NOT NULL,
    update_time          DATE               DEFAULT SYSDATE NOT NULL,
    delete_time          DATE,
    CONSTRAINT pk_media_assets PRIMARY KEY (media_id),
    CONSTRAINT fk_media_assets_uploader
        FOREIGN KEY (uploader_user_id) REFERENCES users (user_id),
    CONSTRAINT ck_media_assets_owner_type
        CHECK (owner_type IN ('USER_AVATAR', 'QUESTION', 'ANSWER')),
    CONSTRAINT ck_media_assets_status
        CHECK (status IN ('ACTIVE', 'DELETED')),
    CONSTRAINT ck_media_assets_file_size CHECK (file_size >= 0),
    CONSTRAINT ck_media_assets_sort_order CHECK (sort_order >= 1)
);

ALTER TABLE users
ADD avatar_media_id NUMBER;

ALTER TABLE users
ADD CONSTRAINT fk_users_avatar_media
FOREIGN KEY (avatar_media_id) REFERENCES media_assets (media_id);

CREATE INDEX idx_media_assets_owner
    ON media_assets (owner_type, owner_id, status, sort_order);

CREATE INDEX idx_media_assets_uploader
    ON media_assets (uploader_user_id);
```

## 7. API 设计

### 7.1 头像相关接口

#### `POST /api/users/me/avatar`

作用：

- 上传或替换当前登录用户头像

请求：

- `multipart/form-data`
- 字段：`file`

返回建议：

- `media_id`
- `public_url`
- `mime_type`
- `file_size`

#### `GET /api/users/me/avatar`

作用：

- 查询当前用户头像信息

#### `DELETE /api/users/me/avatar`

作用：

- 软删除当前头像

第一版也可以不单独做这个接口，而是在重新上传头像时直接替换旧头像。

### 7.2 问题图片接口

#### `POST /api/questions/{question_id}/images`

作用：

- 给问题上传配图

请求：

- `multipart/form-data`
- `files[]`

#### `GET /api/questions/{question_id}`

增强返回：

- 在问题详情里增加 `images: []`

#### `DELETE /api/questions/{question_id}/images/{media_id}`

作用：

- 删除问题配图

### 7.3 回答图片接口

#### `POST /api/answers/{answer_id}/images`

作用：

- 给回答上传配图

#### `DELETE /api/answers/{answer_id}/images/{media_id}`

作用：

- 删除回答配图

#### `GET /api/questions/{question_id}`

增强返回：

- 回答对象中增加 `images: []`

## 8. 响应结构建议

建议统一媒体对象格式：

```json
{
  "media_id": 101,
  "owner_type": "QUESTION",
  "owner_id": 62,
  "public_url": "/uploads/questions/20260422_ab12cd34.jpg",
  "mime_type": "image/jpeg",
  "file_size": 182734,
  "sort_order": 1,
  "status": "ACTIVE"
}
```

### 8.1 问题列表增强建议

`GET /api/questions` 后续可选补充：

- `author_avatar_url`

### 8.2 问题详情增强建议

问题详情建议返回：

- `author_avatar_url`
- `images`

每条回答建议返回：

- `author_avatar_url`
- `images`

每条评论建议返回：

- `author_avatar_url`

## 9. 业务规则

### 9.1 头像规则

- 每个用户同时只有一个当前头像
- 上传新头像时，旧头像置为 `DELETED` 或解除引用
- 只允许图片类型：
  - `image/jpeg`
  - `image/png`
  - `image/webp`
- 单张头像不超过 `2MB`

### 9.2 问题图片规则

- 只有问题作者本人可上传或删除问题图片
- 每个问题最多 `9` 张图片
- 单张不超过 `5MB`
- 只允许图片类型

### 9.3 回答图片规则

- 只有回答作者本人可上传或删除回答图片
- 每个回答最多 `6` 张图片
- 单张不超过 `5MB`

### 9.4 删除规则

- 图片删除先走软删除
- 不立即物理删除文件
- 后续可通过清理脚本定期删除 `DELETED` 文件

## 10. 后端实现建议

按当前项目分层，建议新增：

- `app/api/routes/media.py`
- `app/services/media_service.py`
- `app/repositories/media_repository.py`
- `app/schemas/media.py`

另外建议新增：

- `app/core/file_storage.py`

职责建议：

- `route`
  - 处理上传请求
  - 做登录态和 owner 权限校验入口
- `service`
  - 处理上传规则、数量限制、替换逻辑
- `repository`
  - 负责 `MEDIA_ASSETS` 和 `USERS.avatar_media_id` 读写
- `file_storage`
  - 负责本地文件落盘、删除、URL 生成

## 11. 前端改造建议

### 11.1 登录后头像展示

建议在页面里补：

- 当前用户头像
- 问题作者头像
- 回答作者头像
- 评论作者头像

### 11.2 发帖与回答上传图片

建议在：

- `app/web/home.html`
  - 发帖弹窗增加图片上传
- `app/web/detail.html`
  - 回答框增加图片上传

### 11.3 展示形态

第一版建议：

- 小缩略图
- 点击可查看原图

不建议第一版就做：

- 拖拽排序
- 图片裁剪
- 相册灯箱
- 多媒体混合上传

## 12. 测试计划

建议至少覆盖：

1. 用户上传合法头像成功
2. 用户上传非图片失败
3. 用户上传超大头像失败
4. 用户替换头像成功
5. 问题上传图片成功
6. 非作者上传问题图片失败
7. 回答上传图片成功
8. 问题详情正确返回图片列表
9. 回答正确返回图片列表
10. 删除图片后状态更新正确

## 13. 推荐开发顺序

建议按以下顺序落地：

1. 新增 `MEDIA_ASSETS` 表与 `USERS.avatar_media_id`
2. 实现头像上传与展示
3. 实现问题图片上传与详情展示
4. 实现回答图片上传与详情展示
5. 最后再考虑评论发图

## 14. 当前最推荐的落地范围

如果只做一个适合当前项目阶段的版本，我建议范围收在：

- 用户头像
- 问题配图
- 回答配图

暂不做：

- 评论图片
- 视频 / 音频 / 文件附件
- 对象存储
- 图片审核后台

这套范围最适合你当前的问答社区 MVP，也最容易和现在的 Oracle + FastAPI + 原生网页前端结构接上。
